# Trade-off analysis

What was chosen, what it costs, and what was given up. Alternatives are
discussed only where the project context actually bears on them — several
elements of the stack were specified for this assessment rather than selected,
and those are marked as such.

---

## FastAPI and asynchronous database access

**Chosen:** FastAPI + Uvicorn, SQLAlchemy 2.0 async with asyncpg.

The workload fits async well. Nearly every request is I/O-bound — one or two
Postgres round-trips — and the chatbot adds a call to an LLM that can take tens
of seconds. On a sync stack that one slow request occupies a worker thread for
its whole duration; on async it costs an awaited coroutine.

FastAPI also folds three jobs into one declaration: request validation,
response projection and the OpenAPI document. The API reference in
[`api.md`](api.md) and the contract tests both derive from the same handlers,
so a route cannot drift from its documentation without the schema changing too.

**What it costs**

- **Async is viral and unforgiving.** One blocking call inside a coroutine
  stalls the whole event loop, and the symptom is latency somewhere else
  entirely. The compensating discipline is that `attendance_rules.py` is pure
  and synchronous, and nothing in a request path does blocking I/O.
- **asyncpg binds a connection to the event loop that created it.** This shaped
  the test suite more than the application: `conftest.py` needs a
  session-scoped loop and a session-scoped engine, and integration tests run
  inside a savepoint with an outer rollback. A test module that opens its own
  committed connections (`test_concurrency.py`) interferes with that shared
  engine — a known, unresolved interaction, recorded under
  [Known limitations](#known-limitations).
- **Fewer worked examples.** Async SQLAlchemy has a smaller body of community
  precedent than the sync ORM; some patterns had to be derived rather than
  looked up.

**Alternative considered:** sync SQLAlchemy with a larger worker pool. Simpler
to reason about and to test, but it would have made the chatbot's latency a
capacity problem rather than a waiting problem.

## Supabase PostgreSQL, SQLAlchemy and Alembic

**Specified for this assessment**, so the trade-off discussion is about living
with it rather than choosing it.

What it buys is real: a managed Postgres with backups, connection pooling and
TLS, plus the parts of Postgres this schema leans on hard — `EXCLUDE USING
gist`, partial unique indexes, JSONB, `INET`, enums, and PL/pgSQL triggers. A
large amount of this system's correctness lives in the database rather than in
Python, and that is only possible on a database this capable.

**What it costs**

- **Latency.** The database is remote. Measured from this development machine:
  roughly 2.8 s to connect and ~150 ms per round-trip. That is the single
  biggest influence on the code's shape — it is why `reports.build_grid()`
  loads users, assignments, shifts, records and leave in one batched pass
  instead of querying per employee. An N+1 over a 30-day report would be
  tens of seconds of pure network time.
- **Two connection modes, easy to get wrong.** The direct connection (5432) and
  the transaction pooler (6543) behave differently: pgbouncer's transaction
  mode is incompatible with asyncpg's prepared-statement cache, so pointing the
  app at the pooler requires `DB_USE_PGBOUNCER=true`, and Alembic should use
  the direct connection. A `PostgresDsn` validator rejects a sync driver
  outright, because the first symptom otherwise is a `ModuleNotFoundError` for
  psycopg2 that says nothing about the real mistake.
- **Connection ceilings bound horizontal scaling** more tightly than CPU does.

**Alembic specifically.** Migrations are the only way tables are created —
nothing calls `create_all()`, including the test suite. The cost is that
autogenerate does not see everything: **exclusion constraints and triggers
cannot be autogenerated or diffed**, so the assignment-overlap `EXCLUDE` and
the audit append-only trigger are written out by hand in the migration and
documented at the model. `alembic check` will therefore never warn if one is
dropped.

## JWT authentication and RBAC

**Chosen:** stateless Argon2id + JWT bearer tokens, with a revocation list.

Argon2id is the current OWASP recommendation, used via `argon2-cffi` directly
rather than through passlib — which is unmaintained and adds a layer that only
obscures the parameters. Work factors are configurable, and a settings
validator refuses weakened parameters unless `APP_ENV=test`: the convenience
that makes the suite fast is otherwise one stray environment variable away from
making production hashes cheap to crack.

RBAC is deliberately small — two roles, `employee` and `admin` — and
centralised in `app/api/deps.py`. A route declares `CurrentUser` or
`CurrentAdmin` rather than calling a checker, so a protected route cannot be
written by forgetting to protect it. That is testable as a property rather than
case by case: the RBAC tests enumerate privileged routes from the OpenAPI
schema, so a new admin route is covered the moment it is added.

**What it costs**

- **A JWT cannot be withdrawn**, which is the whole point of it being
  stateless. Logout therefore records the token's `jti` in `revoked_tokens`,
  and every authenticated request checks that list — giving back the database
  round-trip that statelessness was meant to save. `get_current_user` also
  reloads the user on every request rather than trusting the token's claims, so
  deactivating someone takes effect immediately rather than whenever their
  token happens to expire. **This is a deliberate trade of performance for
  revocability**, and at this scale it is clearly the right side of it.
- **`revoked_tokens` grows** and nothing prunes rows past `expires_at` today.
- **Two roles is not enough for a real deployment.** There is no manager or
  team-lead role, so there is no "see my team but not the company" tier:
  `/reports/*` is all-or-nothing. The demo data models managers as
  `departments.head_id` and `users.manager_id` — reporting lines that grant no
  privileges — rather than inventing a role to make a demo look better.
- **No refresh tokens.** A 60-minute expiry means re-authenticating, which is
  acceptable for an internal tool and would not be for a mobile app.

**Alternative considered:** Supabase Auth. It would have supplied sessions,
refresh and social login for free, but authorisation still has to be enforced
against this schema's own `users.role`, and it would have split identity across
two systems.

## Streamlit as the dashboard

**Specified for this assessment.** It buys an enormous amount of UI for very
little code — tables, filters, charts and forms without a build step, a router
or a component library.

**The binding constraint was architectural, not visual:** the dashboard calls
the API over HTTP and never touches the database. `dashboard/api_client.py`
imports nothing from `app`. That keeps a single enforcement point for
authentication, authorisation and validation, and it means the dashboard holds
no database credentials.

**What it costs**

- **The whole script re-runs on every interaction.** State lives in
  `st.session_state`, and anything expensive must be cached deliberately.
- **Sessions are per-replica.** The auth token lives in Streamlit's session
  state, so more than one dashboard replica needs sticky sessions at the proxy;
  a user moved between replicas is signed out.
- **Cached role, stale view.** The role is read from `/auth/me` at sign-in and
  held in session state, so a role changed in the database only takes effect
  after signing out and back in. This is a real and confusing failure mode
  worth knowing about.
- **Limited control over layout and interaction.** Routing is a sidebar
  selection, not URLs. One consequence shaped the code: the view modules live
  in `dashboard/views/`, **not** `pages/`, because Streamlit auto-publishes a
  `pages/` directory as navigable URLs — including the admin ones.
- **The server renders, so UI testing is awkward.** `streamlit.testing.v1.AppTest`
  gives in-process smoke tests, but those stub the API — and a stub that
  invented a response shape the server never returned is exactly how a
  page-envelope mismatch on `/admin/users` got past the tests. The fix was
  contract tests derived from the OpenAPI document, which is a lesson about
  stubs generally rather than about Streamlit.

**Alternative:** a React/Next.js SPA. Better UX control and a genuinely
stateless frontend, at several times the implementation cost — not the right
trade for an assessment deliverable.

## OpenRouter and LLM integration

**Specified:** OpenRouter with `stepfun/step-3.7-flash`.

OpenRouter exposes an OpenAI-compatible API, so the official `openai` SDK is
used unchanged against a different `base_url` — no bespoke HTTP client, and
swapping models is a one-line `.env` change.

**What it costs**

- **Reasoning cannot be switched off** on this model; only the effort level
  (`low`/`medium`/`high`) is a lever, and reasoning tokens bill at the
  completion rate.
- **`OPENROUTER_MAX_TOKENS` is not optional.** Without an explicit cap the
  provider reserves the model's full context against the account balance,
  which fails with a 402 on a small balance and bounds nothing on a large one.
- **A misconfigured base URL fails opaquely.** Pasting the full
  `.../chat/completions` endpoint where the base URL belongs produces
  `/chat/completions/chat/completions` and a bare 404 that says nothing about
  the cause — so a field validator trims that suffix rather than failing.
- **Non-determinism and latency** are inherent. The mitigation is structural,
  not prompt-level: see the next section.
- **Third-party data exposure.** Tool *results* are sent to OpenRouter.
  `redact()` runs over them first, and the raw rows never leave — but this is
  still an external processor seeing attendance data, which is a procurement
  and privacy question before it is a technical one.

**Failure isolation:** the LLM is a leaf dependency. If it is down or no key is
set, `POST /chat` returns **503** and nothing else is affected — attendance,
reporting and administration have no runtime dependency on it.

## Deterministic analytics versus LLM explanation

This is the most consequential design decision in the project.

**Every number is computed in Python/SQL in `app/services/reports.py`. The
model never computes, never sees SQL, and never receives rows the caller may
not read.** It selects a tool, supplies validated arguments, and phrases the
result.

The reasoning is simple: an attendance figure is used to pay people and to
manage them. A number that is right 97% of the time is not acceptable, and —
worse — an LLM's wrong number arrives with the same confidence as a right one.
Routing arithmetic through a model would also make the same question answerable
differently on two days, which is indefensible in a dispute.

The same split is what makes authorisation enforceable. `_resolve_subject()` in
`app/ai/tools.py` pins a non-admin to their own records **before** any query
runs, and raises `NotAuthorizedError` rather than silently rewriting the
request — a visible refusal rather than a disguised one. Had the model held the
query, authorisation would depend on prompt adherence, which is not a security
control.

**What it costs**

- **The assistant can only answer what a tool covers** — six read-only tools
  today. A question outside them gets a refusal, not an improvised answer.
- **More code.** Each capability is a Pydantic argument model, a handler and a
  tool schema, rather than a sentence in a prompt.
- **The `grounded` flag is load-bearing.** It is false when no tool backed the
  answer, and clients must present that differently from a database figure. A
  client that ignores the flag undoes the protection.

**Alternative rejected: text-to-SQL.** It would answer open-ended questions,
and it would make every authorisation decision depend on generated SQL. For
payroll-adjacent data that is not a trade worth making.

## PII redaction and append-only audit logs

**Redaction happens on the way out, not by trusting callers.** A
`RedactingFilter` is attached to the root handler *and* to the uvicorn loggers,
including `uvicorn.access` — which does not propagate to root, so without that
the one log everybody tails would be the one that is not scrubbed. An access
line such as `GET /api/v1/admin/departments?search=jane.doe@acme.com` is a real
PII leak into a file that outlives any decision about who should see it.

**Audit rows are staged in the caller's transaction**, so there is no window in
which the trail claims something that never happened. The table has no
`updated_at` — a column implying mutability — and a `BEFORE UPDATE OR DELETE`
trigger raises `insufficient_privilege`, so the trail is append-only *in fact*
rather than by convention: neither a future endpoint nor a direct `psql`
session can rewrite it.

**What is deliberately not recorded:** passwords, JWTs, API keys, and the text
of chatbot questions. A chat audit row keeps the question's *length*, the tools
that ran and whether the answer was grounded. Attendance questions carry
personal detail — "why was I marked absent the day of my hospital appointment"
— and an audit trail is read by people who need to know that a query happened,
not what was confided in it. The cost is that a disputed answer cannot be
reproduced verbatim; the tool names and arguments are what make it
reconstructible.

**Report reads are audited too**, because reports expose other people's
attendance, so who looked is itself worth recording. The filters are kept; the
results are not.

**Costs**

- Redaction is **regex-based** and therefore both over- and under-inclusive: it
  can mangle a legitimate string, and it cannot catch a name in free text.
- The audit table **grows without bound**; no retention or partitioning policy
  exists.
- The append-only guarantee creates the conflict below.

## Audit retention versus the right to erasure

**This is unresolved, deliberately, and it needs a policy decision rather than
a patch.**

`audit_logs.actor_id` is declared `ON DELETE SET NULL` so that deleting a user
never erases the trail of what they did. But the append-only trigger rejects
**any** `UPDATE` on the table — including the one PostgreSQL issues internally
to apply that `SET NULL`. The two mechanisms contradict each other.

The consequence, verified empirically:

```
DELETE BLOCKED: InsufficientPrivilegeError:
audit_logs is append-only: UPDATE is not permitted
```

**A user with audit history cannot be deleted.**

It is not reachable through the API today — there is no delete-user endpoint —
so nothing is currently broken. But it is a latent contradiction between two
real obligations:

| Obligation | Pulls toward |
| --- | --- |
| An audit trail must be tamper-evident and complete; a disputed payroll decision may need to be reconstructed years later. | Never mutate `audit_logs`. |
| A data-subject erasure request (GDPR Art. 17 and equivalents) may require removing a person's identifying data. | Mutate or remove rows that identify them. |

Three options, each a different policy:

1. **Keep the trigger; never hard-delete users.** Deactivate instead
   (`is_active = false`, `employment_status = terminated`). The trail stays
   intact and the FK's `SET NULL` never fires. This is what the system does
   today by accident rather than by decision, and it does not satisfy an
   erasure request.
2. **Relax the trigger to allow exactly `actor_id → NULL`.** Deletion works and
   the trail survives with an anonymous actor, at the cost of the guarantee no
   longer being absolute — the trigger becomes a rule with an exception, and
   exceptions get extended.
3. **Change the FK to `ON DELETE NO ACTION`** and require an explicit,
   audited anonymisation step before a user can be deleted. Most honest, most
   work.

The schema and trigger are left exactly as they are. **This needs a decision
from whoever owns the data-retention policy, not from whoever is next in the
code.**

## Docker deployment and migration strategy

**One multi-stage image, two final targets.** `api` and `dashboard` build off a
shared runtime layer but are separate stages, because `HEALTHCHECK` is baked
into the image: sharing a stage would give the dashboard the API's probe, which
it can never pass. Both run as a non-root user.

**Migrations are a profile-gated one-shot service**, never part of `up`. With
more than one API replica, migrating on startup means every replica races
`alembic upgrade head` against the same database. The cost is an extra manual
step, and a deploy that forgets it starts an API against an old schema — a
real failure mode, mitigated only by documentation today.

**`docker-compose.prod.yml` is standalone, not an override.** Compose merges
volume lists by target rather than replacing them, so layering it over the dev
file would silently keep the bind mounts and `--reload`. Two files that share
structure will drift; the alternative silently ships a development server.

**Secrets stay out of images.** `.env` is supplied via `env_file` at runtime and
excluded by `.dockerignore` along with `.git`, `.streamlit` and `*.log`.
Compose `env_file` is adequate for a single host and is *not* a secrets manager
— on a real deployment this should be Docker secrets, a cloud secret store, or
injected environment from the orchestrator.

**Not provided by this repository:** a reverse proxy, TLS certificates, or any
orchestration beyond Compose. Both services bind `127.0.0.1` on the assumption
that something terminates TLS in front of them.

## Cross-cutting trade-offs

### Scalability

| Dimension | Position |
| --- | --- |
| API | Stateless apart from the pool; scales horizontally until Supabase's connection ceiling binds. |
| Dashboard | **Not** stateless — session-affine. Needs sticky sessions beyond one replica. |
| Reports | Bounded by a 366-day range cap and a single batched grid load; the grid is built in memory, so a very large organisation over a long range is a memory concern before it is a query concern. |
| Chatbot | Bounded by the provider, not by this system. |
| Background work | **There is none.** No scheduler, no queue, no nightly job to mark absences. Absence is derived at read time instead, which is why it needs no job — a deliberate simplification. |

### Reliability

Liveness and readiness are separate probes: `/health` answers without the
database, `/health/ready` runs `SELECT 1`. The LLM is isolated behind a 503.
Concurrency correctness rests on database constraints — the unique
`(user_id, work_date)`, the GiST `EXCLUDE` on assignments, and a `FOR UPDATE`
lock on punch-out — rather than on application checks, and that is tested with
genuinely concurrent connections rather than within one transaction.

There is no retry or circuit breaker around the database, and no graceful
degradation if Supabase is slow.

### Maintainability

Routers stay thin; logic lives in services; the rules engine is pure and
database-free, so timezone, grace-period and overnight behaviour is unit-tested
without Postgres. Comments throughout explain *why* rather than *what* — this
repository is read by a reviewer as much as it is run.

The cost is more files and more indirection than a single-module app would
need, and some duplication between ORM constraints and Pydantic validation.

### Security

| Control | Where |
| --- | --- |
| Argon2id, OWASP parameters, floored outside tests | `core/config.py`, `core/security.py` |
| Identical response and timing for unknown email vs wrong password | `services/auth.py` |
| Registration can never grant admin (two independent layers) | `schemas/auth.py`, `services/auth.py` |
| Centralised RBAC, enumerated from OpenAPI in tests | `api/deps.py` |
| `extra="forbid"` on every write schema | `app/schemas/` |
| No raw SQL from user input; LIKE metacharacters escaped | `services/directory.py` |
| CORS wildcard rejected when `APP_ENV=prod` | `core/config.py` |
| Placeholder JWT secret rejected in prod | `core/config.py` |
| Secrets never logged; access log filtered | `core/logging.py`, `core/pii.py` |
| Append-only audit trail, enforced by trigger | migration + `models/audit.py` |
| Authorisation before retrieval in chatbot tools | `ai/tools.py` |
| `FORWARDED_ALLOW_IPS` guards audit-trail client IPs | deployment config |

**Gaps, stated plainly:** no rate limiting on `/auth/login` or `/chat`; no
account lockout; no MFA; no password-reset flow; no CSRF concern only because
there are no cookies; `/docs`, `/redoc` and `/openapi.json` are served in every
environment including production; no automated dependency-vulnerability gate in
CI.

### Performance

The dominant cost is network round-trips to a remote database, which is why
reporting batches its loads. Argon2id is intentionally expensive — roughly
100 ms per hash at OWASP parameters — which is correct for login and is why the
test suite is permitted to lower it under `APP_ENV=test` only. Chatbot latency
is dominated by the provider and by mandatory reasoning tokens.

No caching layer exists. Report results are recomputed per request, which keeps
them correct by construction and is affordable at this scale.

## Known limitations

1. **Leave has no REST endpoint.** `LeaveRequest` is fully modelled,
   constrained, and honoured by reporting — approved leave suppresses an
   absence — but no route creates, lists, approves or rejects one. Rows exist
   only via the seeder or direct SQL. This is the largest feature gap.
2. **No manager role**, so no team-scoped reporting tier.
3. **No attendance-correction endpoint**, no role-change endpoint, no
   delete-user endpoint. All are out-of-band operations.
4. **`/docs` is exposed in production.**
5. **The audit/erasure conflict** above.
6. **One test is failing**: `tests/test_reports_api.py::test_trend_granularity_changes_the_bucket_count`,
   most likely because `tests/test_concurrency.py` opens committed connections
   on the shared session-scoped engine. The suggested fix is to give that
   module its own engine. *(Reported from the last run of the suite; no tests
   were run while writing this document.)*
7. **`revoked_tokens` is never pruned**; `audit_logs` has no retention policy.
8. **No background scheduler**, so nothing marks holidays or closes stale open
   punches.
9. **The demo seeder has not been run or verified** against a live database.

## Future improvements, roughly in order of value

1. Leave endpoints — create, list, approve, reject — and the dashboard views
   for them.
2. Resolve the audit/erasure policy and implement whichever option is chosen.
3. An attendance-correction endpoint, so the correction path the audit trail
   already models is reachable through the API.
4. A manager role with department-scoped reporting.
5. Rate limiting and account lockout on authentication.
6. Fix the test-isolation interaction; add a dependency-audit gate to CI.
7. A retention/partitioning policy for `audit_logs` and a prune job for
   `revoked_tokens`.
8. Make `/docs` conditional on `APP_ENV`.
9. Refresh tokens, if a mobile client is ever in scope.
